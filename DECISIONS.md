- **D-036 (2026-10-23, R1, FULL_REVIEW F-01):** Schedule awareness. The user's schedule answer was ambiguous to the PM, so the rule is a setting: `SCHEDULE_MODE=honour` (default) | `ignore` (the old "every day when ready"; t6 and t4 `--schedule-mode`). (1) T2 reads the REST schedule object of every subscription into the new `Integration.Tableau_Schedule` (frequency, weekdays, month day tokens, start time, interval hours, state; DDL scripts/sql/R1_schedule_schema.sql + rollback, tagged R1_schedule_schema) and the new nullable column `Tableau_Subscription.ScheduleId`. Checked against the 9 real UAT schedules. (2) OCCURRENCE = a Singapore date on which the schedule fires (time of day ignored). It can be satisfied on that date or up to `SCHEDULE_CATCHUP_DAYS` (default 3) later, never beyond the day before the next occurrence. "1st day of month" is the calendar 1st and is never moved: if that day has no ETL the report goes on the first following day the data is ready (inside the 3 days), else a `missed_due` alert on the day after the window and the occurrence is dropped. (3) A send-log row Sent, Claimed or TimedOut with a SendDate inside the window satisfies the occurrence, so the same occurrence is never sent twice (Released, Failed, DryRun do not). The claim-first once-per-day slot is unchanged. (4) Only DUE subscriptions are evaluated further: the 15:30 "not ready" alert and the mapping_stale alert apply to due subscriptions only; t4 refreshes only workbooks with a subscription that is due and not yet sent. (5) Fail closed: a missing, suspended, unsupported (interval over 24 h, customised monthly, unknown frequency) or stale (older than MAPPING_MAX_AGE_H) schedule means not due; missing/unsupported raise a `schedule_unknown` alert, a suspended schedule is quiet. (6) Occurrences before the takeover (`PausedAt`) belong to the old Tableau subscription and are ignored; an occurrence on the takeover day counts only if its start time is later than the pause time ("taken_over_today", not an error). With SCHEDULE_MODE=ignore t6 still never sends on the day the subscription was paused. (7) Guesses to verify on prod: Tableau schedules run in Singapore time; monthly day 31 fires on the last day of a short month. t11 does not take over a subscription whose schedule t6 cannot evaluate or that has no schedule id.
- **D-037 (2026-10-23, R1, F-06):** SES reply handling. Only a 5xx reply to the end-of-message dot that matches a small allow-list (`KNOWN_REJECTIONS`: `554 Message rejected: Email address is not verified`, `554 Message rejected: Missing final '@domain'`; FROM RECALL of SES behaviour, VERIFY at the first live test) is a deterministic non-delivery: row `Failed` with prefix `REJECTED:`, slot freed, alert, not retried the same day (a person sets Failed to Released to retry). Everything else after the content (other 5xx, 4xx, timeout, drop) stays ambiguous/Claimed as in D-027/D-033. The SES message id from the 250 reply is stored in the log row Message (`smtp_id=`), no address. Preflight: before the first real claim of a `--ses` run, EHLO/STARTTLS/LOGIN/MAIL FROM/RCPT TO for the sender and one allow-listed recipient, RSET, QUIT, no DATA; refusal = no claim, one alert, exit 1. Circuit breaker: any non-250 final reply after the content, or two consecutive SMTP failures, stops further claims in that run (the rest stay unclaimed), one alert with the reply text (addresses removed), exit 1.
- **D-038 (2026-10-23, R1, F-08/F-09):** T2 resilience. T2 takes the shared PAT applock (retries 10 x 30 s), logs to out/t2_sync.log with a RUN SUMMARY line, exit 0 / 2 (written, some items skipped, alert) / 1 (failed entirely, nothing written, alert). Per-workbook, view, subscription and schedule isolation: the failing item is logged and skipped, its existing rows stay active and keep their old LastSeenAt (they go stale: t6 stops sending after MAPPING_MAX_AGE_H and alerts); nothing is deactivated because a read failed (the MERGEs exclude skipped workbooks and subscriptions); the 25% partial-read guard counts the protected rows. ## Q1 approach: building the table to pipeline map
No full map exists. Do not try to map every table in the DWH. Build it from the demand side:
1. Use the Tableau Metadata API to list the upstream tables of the data sources behind the affected reports. This is a small subset of the DWH.
2. For those tables only, propose the loading pipeline from the DWH itself: SQL Agent job step commands (`msdb.dbo.sysjobsteps`), SSIS package destinations (parse the `.dtsx` XML or `SSISDB`), and stored-procedure writes (`sys.dm_sql_referenced_entities`, which reports `is_updated`).
3. A person confirms each proposal. Store the confirmed rows in the new registry table.
4. Going forward, deploying a pipeline includes registering the tables it loads.
A runtime check (a table's last update time against ETL_Master_Log end times) can help validate guesses but is not reliable enough to be the source of truth.
