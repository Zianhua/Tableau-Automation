# Known limitations and assumptions

Short reference. Decisions are in DECISIONS.md.

- **Reports are exported as each subscriber (D-063, 2026-11-03)**, using the shared admin account in a separate session (`RENDER_AS_SUBSCRIBER=1`), so per-user filters show that person's data. Proven on UAT with a normal user only; NOT yet proven with a per-user-filter workbook (the user runs that test himself). In production the Tableau admins choose the shared admin account, and a password change there breaks exports.
- **Excel/CSV and other-database parts have no freshness check** (D-021, D-053). The report sends when the warehouse part is ready; a source whose connections are all positively non-DWH is deemed ready (`NotChecked`). A report whose sources are all files is sent on schedule with no check at all. A stale file or an old copy of another database is NOT noticed. An embedded Tableau extract of a file is never refreshed by the script (it has no pipeline), so the report is sent with that extract's old data unless Tableau's own schedule refreshes it.
- **Freshness is checked per pipeline, not per table.** A pipeline that ran today counts as ready even if one table in it failed to load.
- **UAT cannot reach the prod DB** (D-012). Refreshes and live-connection PDFs fail there. Test with purpose-built UAT reports. A real end-to-end test of prod data is only possible on prod.
- **Dev DWH is used for development** (D-011). The readiness check must be repointed to the DWH the Tableau sources really read before go-live.
- **Subscription fidelity.** The script keeps target, format (PDF/image), subject and message per subscription. Per-subscription custom views and view filters are not visible through the API and may be lost.
- **Suspended is no special category** (D-046, reverses D-023). Every in-scope subscription that still exists in Tableau is taken over and sent, also one that is suspended today (30 of 54 on UAT). Whatever must not be sent has to be deleted in Tableau by the user BEFORE go-live (scripts/review_list.py lists them). The script cannot tell "suspended on purpose" from "suspended by Tableau after failures".
- **Send format and size.** The SES/Outlook attachment size limit is unknown (D-019). Very large PDFs may fail.
- **Only schedule-based subscriptions are in scope (D-044).** Data-driven ("when data refreshes") subscriptions are ignored by design: not taken over, not paused. Not an open item.
- **Static tables.** `dbo.SalesChannel_Excel` (deprecated, 13 rows) has no freshness check. A table must not be in both the static list and the registry; no database trigger enforces it (D-081), the daily mapping sync alerts when it happens. `Dimension.MultipleAccounts_ManualImportData` is mapped to DailyETL on the user's word, but no loader exists in the dev DWH, so readiness only reflects whether DailyETL ran.
- **OAO and LeadGen share one pipeline** (D-025). An OAO failure also holds back LeadGen reports.
- **Custom SQL data sources** are mapped later (D-024). Until mapped, those workbooks do not send (fail closed).
- **Pilot workbook (D-022b: CFD Accounts, Middle Office).** The older pilot subscription on it was taken over and then deleted in Tableau on 2026-10-26; CFD Accounts has a new test subscription, taken over at 18:11 the same day. There is still no production pilot.
- **Refresh gate sees completed ETL rows only** (T4, pipeline-level, G12). `ETL_Master_Log` has JobID, PipelineName, EndTime (NOT NULL) and Success. An ETL rerun in progress, or a run that crashed without writing a row, is invisible: the earlier success of the day still counts. If an ETL completes after our last refresh was submitted, the extract is refreshed again (max 3 attempts per target per day).
- **Extracts that are never refreshed by the script.** Extracts whose tables are all static, and embedded extracts (need a workbook refresh, not built) have no pipeline to gate on, so T4 skips them. (A source whose connections are all positively non-DWH is `NotChecked`, counts as ready and has nothing to refresh: D-053.)
- **A queued/running refresh job already on Tableau** for the data source (for example from the old refresh job, D-017; for a taken-over extract the old job is switched off, D-080) makes the script skip that target for that run. Matching is by data source name (job title), conservative.
- **UAT is `http://`**, so the PAT crosses the network in clear text. Use HTTPS on prod if available.
- **Custom SQL with Tableau parameters.** Queries containing `<Parameters.X>` placeholders do not parse, so their data source fails closed (NotReady) until mapped by hand (D-031). Same for custom SQL that calls user-defined functions, uses APPLY, UNION, INTO or temp tables.
- **Send path run for real only once** (T6/T7): one real send of the older CFD Accounts pilot subscription through the project owner's Gmail on 2026-10-26; everything else used local SMTP. SES behaviour (STARTTLS login, sandbox, verified sender, message size cap, throttling) is untested.
- **Wide crosstab images** (for example Sales Channel - Daily Active Clients) are capped at 3200 px wide and come out as unreadable slivers; the script warns and lists them but still sends. The fix is a report-design change (subscribe to a dashboard). The crosstab/Excel export design is parked (2026-11-03).
- **Alert de-duplication uses a local file** (out/t6_alert_state*.json). If the job moves to another host the file is not shared, so one alert per day may repeat once.
- **An error reply after the message content** (for example 451) is treated as ambiguous and leaves the claim, so a human checks; this trades a possible missed report for never sending twice.
- **One PAT, one session at a time.** t4_refresh.py and t6_send.py share the applock TABLEAU_PAT_SESSION. While one runs (t4 can wait up to 40 min for refreshes), the other skips its run and retries 15 minutes later, so a report can be delayed. A separate PAT per script (D-017 allows one for the new scripts, not two) would remove this.
- **Mapping freshness is checked per subscription and workbook change time only.** The live data source count of a workbook is not compared with the mapped DataSourceCount (no cheap REST call); a data source added to a workbook without the workbook being republished is not detected until the next T2 sync. T2 runs ONCE A DAY (about 07:50, D-046) and must run at least daily (26 h limit) or nothing is sent. A workbook republished after the daily sync waits for the next sync: t6 does not send it (`awaiting_sync`, INFO log and a line in the daily summary, no alert). Cost: a republished workbook can miss one day's send; rerun T2 by hand to release it.
- **Local test deliveries end as Released**, so a local --execute run does not block the real send, but it also sends again on every run.
- **Old .eml files in out/** (from the preview work) contain a real address; out/ is gitignored.
- **Takeover pilot (T11a, D-035).** t6 sends only subscriptions taken over by t11_pause.py; t4 refreshes only extracts behind taken-over workbooks (default `--scope takeover`; `all` after the pilot). Nothing is taken over until the allow-list is set (TAKEOVER_WORKBOOK_IDS or --workbooks).
- **Pause must precede the first send.** A subscription must be paused (t11 --execute) BEFORE the first t6 --execute send for it, else Tableau and the script both mail it. t6 enforces it (needs PausedAt and a suspended subscription in Tableau), the schedule order t11-then-t6 is an ops duty.
- **Resumed by a human = no mail that day.** If someone resumes a taken-over subscription, t6 does not send it and, once t11 has paused it again, not for the rest of that Singapore day (the old subscription may have mailed already). Between a resume and the next t11 run (up to 15 min) Tableau itself may send it.
- **The library's pause request omits `message`.** tableauserverclient 0.42 `subscriptions.update` sends subject, formats, page size, orientation, suspended, schedule id and sendIfViewEmpty but not the message. Whether Tableau keeps the message is unverified (no write was run); t11 reads the subscription back and halts on any difference. A subscription on an on-the-fly schedule (no schedule id) may be rejected by the update; that is reported as a failed pause.
- **Workbook that drops to one data source** leaves T2 scope, its subscriptions become inactive, and a taken-over report silently stops (the old subscription stays paused). Restore by hand. A workbook that gains a source starts being sent by the script (it must be taken over first, else t6 does not send it).
- **Auto-suspended subscriptions.** Tableau may suspend a subscription after repeated failures. Since D-046 such a subscription is taken over and sent like the others (backup row only, nothing to pause). `--restore` simply un-suspends it, so a subscription Tableau had suspended for failures comes back active.
- **Deleted in Tableau** = silently dropped by the script (T2 deactivates it); nobody is told that the report stopped.
- **Backup table is the only record of a takeover** (plus out/t11_backup JSON on the host that ran t11). Do not drop it before restoring.
- **Schedules are honoured (D-036), with a setting.** A report goes out only on a day its Tableau schedule fires (or up to 3 days later if the data was not ready), once per due day. Time of day is ignored: a 06:00 report goes out whenever its data is ready that day. Intervals over 24 h, customised monthly schedules and unknown frequencies are not supported (not sent, alert). Assumed, not verified on prod: Tableau schedules run in Singapore time; monthly day 31 fires on the last day of a short month. `SCHEDULE_MODE=ignore` restores the old every-day behaviour.
- **The CFD Accounts v2 test subscription is outside T2's scope.** Its workbook has one data source (scope is more than one, D-007/D-038). The original CFD Accounts workbook (2 data sources) now has its own test subscription (2026-10-26) and is in scope.
- **SES behaviour is unverified.** The list of replies that prove "not queued" (`KNOWN_REJECTIONS`) is from recall; preflight, circuit breaker and message-id capture were tested only against a local stub server. Verify at the first live test.
- **Markers and alert state are files on the host that runs the scripts.** daily_summary only sees runs from that host.
- **The kill switch stops the scripts, not Tableau.** Taken-over subscriptions stay paused while it is on, so those reports stop; restore them (runbook section 7).
- **T2 skipped items go stale instead of failing at once.** A skipped workbook keeps working until MAPPING_MAX_AGE_H (26 h), then t6 stops sending it and alerts; the T2 run itself alerts (exit 2) immediately.
- **Load defaults are guesses** (one refresh at a time, 20 s between exports, 10 sends per run). A morning with many due reports may take several 15-minute runs; they queue naturally. Tune in the pilot.
- **Dry runs sign in to Tableau** (to read the live subscription) and so take the PAT lock while they read.
- **The daily summary "due but not sent" covers taken-over subscriptions only** and cannot see allow-lists (it shows the t6 counter `no_allowed_recipient` instead).
- **Real mail path is provider-neutral (D-043).** Tested only against local stub servers and one real Gmail send. The list of replies that free a slot after the message exists for SES only (from recall); for Gmail and generic servers nothing does, so any post-message error stays Claimed for a person to check. Gmail rewrites From to the authenticated account; its limits (about 500 recipients a day, 25 MB) are from memory.
- **Event log signal needs the source registered once as administrator** and does not itself page anyone; point monitoring at it (RUNBOOK section 1). Not tested against a real Event Log in the checks (the call is faked).
- **A lagging Metadata response is guarded by drop checks** (data sources or tables fewer than stored): the workbook is skipped and goes stale (alert, exit 2) until a clean read or until a person accepts the change for THAT workbook with `t2_mapping_sync.py --accept-drops <workbook id>` (repeatable, each accepted drop is logged). A workbook that really drops to one data source leaves the scope after that explicit acceptance and its rows are deactivated. A table swapped for another table (same count) is not detected.
- **Restoring after the day's send** may lead to a second (native) mail later that day. Since R5 `--restore` refuses in that case unless `--allow-restore-after-send` is given.
- **Alert retry:** an alert with an unknown outcome is sent once more, so it can arrive twice.
- **t4 gives up its Tableau login after about 10 minutes per run** (T4_MAX_LOCK_MIN): a large refresh backlog takes several 15-minute runs.
- **The owner fence is required** (R5, F-2; before that only in Gmail mode). t11 cannot see recipients, so `--execute` with an allow-list requires `--owner-user-id` in every transport; and at most 10 NEW takeovers happen per run (`--max-new` / `TAKEOVER_MAX_NEW`). Other people's subscriptions are never taken over by accident.
- **Deleting send-log rows** that hold a slot (Sent/Claimed/TimedOut) is not blocked by the database (the delete trigger was dropped 2026-11-06; no script deletes from the send log). Deleting one frees the day's slot and allows a second send, so never do it by hand: release the row instead (RUNBOOK section 5).
- **Event-log and log folders can be redirected** (EVENTLOG_DISABLED, LOG_DIR, LASTRUN_DIR, OPS_STATE_DIR) for tests; production leaves them unset.
- **T2 time cap:** at T2_MAX_LOCK_MIN (10) minutes T2 stops reading further workbooks (they stay stale until the next T2 run, which is the next day since T2 runs once a day; rerun it by hand).
- **Takeover-day guard is deliberately conservative** (D-041, kept in D-046): a subscription taken over today is not sent today if its schedule time has already passed, because Tableau may have mailed it. This also applies to a subscription that was already suspended (Tableau did NOT mail it, but the script cannot tell, user decision D-047), so that occurrence is lost until the next one (a month for a monthly report). Since R5 each such skip writes a WARNING to the log and the Windows Event Log (once per subscription and day), `review_list.py` shows the effect in `next_due`, and the rule stays operational: take everything over at least a day before its first due date (RUNBOOK section 14).
- **OPEN QUESTION, not verified (R5, F-3): does a workbook's `updated_at` change when its embedded extract is refreshed?** t6 compares the workbook's live `updated_at` with the value T2 stored when it read the workbook (R5 column `WorkbookUpdatedAt`). If Tableau moves `updated_at` on an embedded-extract refresh (the reviewer believes it may, nobody knows), a workbook whose embedded extract refreshes after the 07:50 sync would count as changed and wait (`awaiting_sync`, INFO log and a daily-summary line, no alert) until the next daily sync, i.e. possibly every day and never sent. By decision nothing was run against Tableau to test this. To check it: refresh one embedded-extract workbook on UAT and compare its `updated_at` (REST workbook, `updatedAt`) before and after. Watch `awaiting_sync` in the daily summary during the pilot: a workbook that stays there day after day is this problem. A NULL stored value (T2 has not run since R5) also waits.
- **No original suspended state is kept** (D-046, R4 dropped WasSuspended). `--restore` un-suspends; to stop script handling a subscription, delete it in Tableau or restore it.
- **The "mail every subscriber" switch is UAT-only** (D-050). `SEND_ALLOW_ALL_UAT=1` works only when `TABLEAU_SERVER_URL` has the host `tableau-uat.example.com`; on any other host it is ignored with a warning and `SEND_ALLOWED_RECIPIENTS` (exact addresses, no wildcards) is mandatory. D-052 item 5 would extend it to the production host; not decided or built.
- **The database and Python guards are hard-coded to the dev warehouse** (`<DEV_DWH_SERVER>` / `CQGlobalSGDW`, D-026): every script and every SQL file refuses to run elsewhere. Production needs a reviewed code change first (docs/DB_CHANGES.md section 4).
- **Test rows in the dev load log (D-052).** `Integration.ETL_Master_Log` has no tag column, so test rows on dev are recognised only by their JobIDs, which are noted locally (currently JobID 397, 2026-11-03; delete only that one at clean-up, after asking the user); anything else that reads the dev load log sees them until they are deleted.
- **`daily_summary.py` crash with error rows: fixed** (backlog R9, 2026-10-26; the test builds the summary from real database rows). Not run for real against a day with error rows.
- **Monthly and weekly subscriptions due on a Sunday or Monday** (no ETL pipeline runs on those days, D-065): they go out on Tuesday through the 3-day catch-up window, one or two days late. On those days the "not ready" alert fires although nothing is wrong (known noise, accepted for now). A catch-up window that ends before the pipelines run again would lose the report; with the default of 3 days it does not.
- **Slow exports (D-064).** Daily T+0 Report takes 12 to 13 minutes per export, so only about two such reports fit in one 25-minute run; the rest go on the next 15-minute run.
- **Automatic registry (D-066).** The pipeline of a table is inferred from the lineage tables plus ETL log timing, not read from the pipeline definitions. The lineage tables name tables only; a table the loaders write without a lineage entry (staging tables, `MultipleAccounts_ManualImportData`, `DastOpenPositionFinal` under another name, `OAO_Lineage` itself: 7 of the 32 hand-made rows) needs a Manual row. Strong timing evidence (80 percent of at least 5 loads ending shortly before one pipeline's log row) outranks the lineage default, so a table loaded just before another pipeline's log row could be attributed to it; the daily report, the cap of 5 moves per run and the alert are the safety net. A table with no ETL log evidence at all is UNCONFIRMED and not registered (D-075): on dev, with no DailyETL row, every table the lineage assigns to DailyETL stays unmapped, so its extract is not refreshed. A moved Auto row changes which pipeline an extract waits for. The primary key allows several pipelines per table, the sync derives one (a multi-pipeline table needs Manual rows). The ambiguity check reads `sys.tables` across all schemas and needs metadata visibility on them; without it a name that exists twice can look unique (DB_CHANGES.md 12.6).
- **Old refresh job switch-off (D-080).** A takeover sets `Active_Flag = 0` in `Integration.ETL_Tableau_ExtractMapping` for the taken-over data source and a restore sets it back. Only rows that were 1 are touched. If a person turns such a row back on by hand, the next takeover run switches it off again. Until the takeover is run, and for every extract that is not taken over, the old job still refreshes as soon as ONE ETL succeeded. A refresh by the old job (before the takeover) does not satisfy t4's schedule rule.
- **Gap between the Tableau delete and its confirmation (D-080).** The schedule rule of t4 applies only once the takeover is confirmed (`NeutralisedAt`). If the run is interrupted between the delete and the confirmation, the task is already gone from Tableau but t4 still treats the extract as not taken over until the next takeover run (daily) confirms it. In that gap the extract is refreshed only for a due subscription. The daily takeover run confirms it at its next start; a person can run `extract_takeover.py --execute` earlier.
- **Extract schedule rule (D-068).** Applies only to extracts whose Tableau task the script took over. Extracts with no Tableau schedule, or a task Tableau still owns, are refreshed only when a dependent subscription is due. A schedule's enabled or disabled state is not looked at (D-080). Only extracts in the mapping (workbooks with a subscription and more than one data source) are seen by t4 at all; the other published extracts and the embedded extracts of workbooks (3 workbook tasks on UAT) stay with Tableau.
- **Extract task takeover deletes the task (D-069).** No per-task suspend exists in the REST API. A restore creates a new task: new id, the task's own priority, failure count and last run time are not restored; full versus incremental refresh is not visible through the API. If the restore cannot run (the schedule was deleted, the data source is gone) the extract has no Tableau refresh until someone creates one by hand; the backup row and out/extract_backup/*.json hold the details. Never run for real yet; add and delete need an administrator token. Restore is untested against a real server.
- **The takeover script is not watched by the watchdog or the daily summary** (it runs once a day, dry run by default). Check its `RUN SUMMARY` line and `out/lastrun/extract_takeover.json`.
- **Taken-over extracts: what is and is not watched (D-073, D-074, D-076).** The schedule of a taken-over task is read by the daily sync (a deleted one is a sync problem); a daily alert names every taken-over extract that is not a t4 candidate, whose schedule is unusable or whose last due occurrence has no successful refresh. The alert is one mail a day per item, and not for an unconfirmed (delete not confirmed) takeover, whose Tableau task still exists. A refresh by the old job (D-017) does not satisfy an occurrence (t4 counts only its own refresh jobs): open question in RUNBOOK section 20.
- **A restored extract is not taken over again** until `NoRetake` is cleared by a person, whatever the allow-list says (D-076). A retried delete is refused when the live task differs from the backup (alert `takeover_changed`); the backup row then stays open until a person restores or closes it.
- **Registry insert limit and young Auto rows (D-075).** At most 5 inserts + moves + removals per run (50 with `--registry-first-run`); an extract with a table from an Auto row younger than 1 day is not taken over before the next daily run. Alert mails are once a day per kind: a second sync on the same day with other changes does not mail again (the log has them).
- **The checks use a rolled-back ETL log fixture (D-077).** `t4_checks`, `t11_checks` and `r1_checks` give every registered pipeline without a log row one year-2001 row inside a rolled-back transaction; they do not depend on dev having a DailyETL row, but they still need at least one real extract with a Ready workbook in the dev mapping. `extract_checks` test_real_derivation reads the real lineage tables and the real ETL log (needs evidence for Nova, LeadGen and OAO tables on dev).
- **Orphan alert in a dry run (D-078).** The alert for a taken-over extract that nothing refreshes is mailed by the daily `extract_takeover` task even while it is a dry run, through `MAIL_TRANSPORT` like the other monitors (local test sink unless `smtp`); with the transport on `local` nobody receives it, and the run exits 1 (`needs_human`) so the scheduler history and the Windows Event Log still show it. Other dry-run items are not mailed.
- **Registry evidence is per pipeline (D-078).** A table is registered only if its derived pipeline matched at least one ETL log row; a table whose log matches belong to another pipeline than the lineage default stays unconfirmed (mail `registry_unconfirmed`) until the log confirms the default or a person adds a Manual row.
- **Test data not removed:** `testdata/dummy_inactive_clients_nova.sql` (the ZZT test clients) exist on dev only; see DB_CHANGES.md section 11. `Dimension.Client_Scoring_Archive_20261026`, `Tableau.vw_Client_Score` and `Integration.MigrateStagedClientData` are the owner's own, not created by this project and not part of the deliverable.
